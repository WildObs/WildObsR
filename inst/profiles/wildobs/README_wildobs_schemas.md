# The WildObs flavour of Camtrap DP

A WildObs data package is canonical [Camtrap DP](https://camtrap-dp.tdwg.org/) plus a small,
fixed set of extensions. Validating one against the upstream profile therefore fails on every
package — not because the packages are malformed, but because the schema has no vocabulary for
what they carry. These five files are the schema that does.

| File | What it describes |
|---|---|
| `camtrap-dp-wildobs-profile-<v>.json` | the `datapackage.json` descriptor |
| `deployments-table-schema-<v>.json` | `deployments.csv` |
| `media-table-schema-<v>.json` | `media.csv` |
| `observations-table-schema-<v>.json` | `observations.csv` |
| `covariates-table-schema-<v>.json` | `covariates.csv`, the WildObs-only resource |

**Do not hand-edit any of them.** They are generated by the WildObs curation pipeline from
the upstream Camtrap DP schemas (vendored in the parent directory) plus a declarative list of
the WildObs extensions, and copied here. The generator refuses to finish if the schemas it
produces no longer describe the curated data packages. A published schema that has quietly
drifted from the data is worse than no schema, because it looks authoritative.

## Versioning

`1.0.2-wildobs.1` means "the first WildObs flavour of Camtrap DP 1.0.2". Bump the suffix when
the WildObs extensions change; bump the leading component when the upstream release does.
Camtrap DP is moving to 2.0.0 — vendor it in the parent directory, point `UPSTREAM_VERSION` at
it, and re-run the generator.

## What WildObs adds

Everything below is **additive**. Every constraint canonical Camtrap DP applies still applies
here, and no standard field is redefined.

### Columns on the core tables

| Table | Column | Why |
|---|---|---|
| `deployments` | `multiSeason_deploymentGroup` | groups repeat deployments at one location across seasons into a single survey |
| `media` | `observationID` | the media→observation link; canonical Camtrap DP has no field for this direction (tdwg/camtrap-dp#377) |
| `media` | `TIR` | whether the file is in the WildObs Tagged Image Repository |
| `observations` | `deltaTime_event` | seconds since the previous event at that deployment, used for independence filtering |

### Descriptor fields

- **`WildObsMetadata`** — what the provider agreed to, what they asked for back, and how the
  survey was run: sharing preference, embargo, funding, deployment tags, and so on.
- **`versionControlWildObs`** — the WildObs version of the package, distinct from `version`,
  which carries the Camtrap DP version the package conforms to.
- **`project.DPID`** — the package id, repeated on the project block.
- **`contributors[].ROR`** — the contributor's organisation, needed to mint a RAiD with a Lead
  Research Organisation. Canonical Camtrap DP has no field for it.
- **`taxonomic[].vernacularNamesEnglish`** — WildObs curates English common names only, so this
  flattens Camtrap DP's language-keyed `vernacularNames` object to one string.

### Vocabulary

- **`relatedIdentifierType` adds `RAiD`.** A RAiD identifies a *research activity* rather than a
  digital object, which is why DataCite has no type for it and why it matters to WildObs: the
  RAiD is the key citation we publish. A canonical export maps it to `Handle`, which resolves
  but loses the fact that it is a RAiD.
- **`taxonRank` adds the intermediate ranks** (`subclass`, `suborder`, `subfamily` and their
  super- counterparts, plus `tribe`). Lepidosauria genuinely *is* a subclass and SERPENTES a
  suborder; rounding them to `class` and `order` to satisfy the upstream enum would record
  something false.

### Shapes upstream forbids

- **`resources[].schema` may be an inline object**, not only a URL. This is the largest single
  divergence from upstream and it is deliberate ([#217](https://github.com/WildObs/cam-DB/issues/217)
  Q1): the inline object is what declares the extension columns and what
  `frictionless::read_resource()` types the CSVs with. Replacing it with a URL would conform and
  discard the documentation.
- **`temporal` may carry one `{start, end}` block per `deploymentGroup`**, alongside the
  package-level extent the standard requires, plus the survey `timeZone`. The public profile
  generator and the interactive map both read those blocks.
- **`media.fileMediatype` accepts a `not_provided` placeholder.** WildObs curates tabular data
  for surveys whose media it does not hold. Those rows are still real observations with real
  timestamps, so the placeholder is accommodated rather than the row discarded.

## How these files are used

The WildObs curation pipeline validates every data package twice: against these files, with
the WildObs extensions in place, and against the upstream Camtrap DP profile, with the
extensions removed. The first check is the one that can reach zero errors, and is intended
to gate whether a package enters the database. The second
measures how far a package is from canonical Camtrap DP, a gap that `as_camtrapdp()` in this
package closes ([WildObsR #113](https://github.com/WildObs/WildObsR/issues/113)).

`as_camtrapdp()` reads these files to decide which fields and values are WildObs additions,
so that it removes exactly those and reports what it removed.

## Publishing

Data packages currently declare the **upstream** Camtrap DP profile, not this one, because
these files do not yet have a public URL of their own. Once they are published, for example
in a public `WildObs/camtrap-dp-wildobs` repository mirroring the TDWG layout and tagged
`1.0.2-wildobs.1`, packages could point `profile` at them instead. That changes what every
downstream consumer sees, so it is a separate decision.
